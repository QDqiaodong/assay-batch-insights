# Longitudinal result warehouse

The warehouse is a standalone, standard-library-only SQLite data mart that
captures the JSON analysis artifacts already produced by `assay_insights` and
lets an analyst rebuild the batch decision that was in force after any
successful import. It does not re-read the original CSVs, re-run calibration
selection or recompute statistics: it stores and cross-checks the facts each
imported report claims. Everything remains original synthetic demonstration
data with no medical, regulatory or laboratory accreditation claim.

Entry point: `python -m assay_insights.warehouse`. The Python API lives in
`assay_insights.warehouse` (`import_manifest`, `build_query`, `render_query`,
`write_query`). The original `load`/`analyze`/`run` functions and the
`python -m assay_insights` CLI are unchanged, and schema 1/2 reports keep
working.

## 1. Import envelope and identity

A manifest is UTF-8 JSON:

```json
{
  "schema_version": 1,
  "import_id": "IMP-001",
  "action": "apply",
  "reports": [{"path": "reports/run-a/report.json", "label": "morning-run"}],
  "corrections": []
}
```

- `schema_version` must be the integer `1`; booleans are not integers and are
  rejected. `action` must be `"apply"`.
- Every business identifier (`import_id`, labels, batch, sample, analyte,
  correction ids ...) must be a non-empty string without surrounding
  whitespace. Labels are unique within one manifest.
- Report `path` values resolve relative to the manifest file's directory.
  Absolute paths, any `..` traversal and symbolic links are rejected, so a
  manifest cannot read outside its own directory tree. Paths are retained only
  as audit labels; machine-absolute paths are never stored or emitted.
- Each manifest and each report is read exactly once into raw bytes; parsing
  and SHA256 both use that single captured buffer.
- A report is accepted only when it is a complete schema 1 or schema 2 report
  generated by this project. A look-alike external summary is rejected because
  it lacks the full required sections. Import validation cross-checks the three
  input SHA256 values, policy, summary counts, ordinary samples, QC groups and
  batch/QC scopes for self-consistency. For schema 2 it additionally rebuilds
  every per-measurement calibration selection, interval coverage, concentration
  formula, QC version scope and the final `reasons` from the claimed
  measurement facts and compares them canonically (order independently) with
  the shipped `analyze` semantics.

### Idempotency and conflicts

`import_id` is the transaction identity:

- Replaying the **same** `import_id` with identical manifest bytes and
  identical report bytes is an idempotent no-op: no rows, source links,
  corrections or knowledge versions are added.
- The same `import_id` with any changed byte (manifest text, label, a report,
  or the correction set) is a hard `ConflictError`; nothing is written.
- Different `import_id` values may reference the same report bytes. Each keeps
  its own source relationship, while the analysis facts are stored once in a
  canonical fact set and are never amplified.

## 2. Canonical fact sets versus raw snapshots

Two levels of identity separate provenance from reusable facts:

- `report_snapshots` holds one row per distinct **captured byte stream**, keyed
  by its raw SHA256, with the original bytes retained verbatim.
- `canonical_fact_sets` holds one row per distinct **canonical content**, keyed
  by a SHA256 over a normalized rendering (sorted business keys, stable JSON).
  The normalized tables `fact_sample_groups`, `fact_qc_groups`,
  `fact_qc_scopes`, `fact_batches`, `fact_calibrations` and
  `fact_measurements` are keyed by this canonical hash.

Re-emitting the same analysis with records in a different order or JSON object
keys in a different order produces a different raw hash but the same canonical
hash. It therefore adds a raw snapshot and a source link, but reuses the single
canonical fact set: measurement and sample counts never grow, and the
longitudinal change view collapses canonical-identical snapshots into one node.

## 3. Stable business keys and corrections

The immutable original identity of an ordinary sample group is
`(report_sha256, batch, analyte, original_sample)` in `sample_identities`.
Schema 1 reports have no `measured_at` or `calibration_id` and are stored as
legacy facts without invented times or versions. Schema 2 keeps the
batch/sample/analyte/replicate measurement identity and rejects conflicting
facts inside one report.

Corrections change business identity in the corrected view only; they never
mutate or overwrite the raw report snapshot or the original facts.

```json
{
  "correction_id": "COR-001",
  "target": {"report_sha256": "...", "batch": "B1", "sample": "S1", "analyte": "nitrate"},
  "operation": "rename_sample",
  "new_sample": "S1-R",
  "reason": "synthetic transcription correction"
}
```

- Operations are `rename_sample` and `withdraw_sample`. `correction_id` is
  unique across the whole database; replaying the same id with the same
  canonical content is idempotent, different content conflicts.
- A target must resolve to exactly one imported **ordinary** sample group. QC
  groups, unknown reports and multiple matches are rejected.
- Corrections always address the immutable original key plus `report_sha256`,
  never a current display name, so a chain of renames stays addressable.
- A rename must not collide with another live display name in the same
  report/batch/analyte scope. Two original samples ending on one name fails the
  whole import. A withdrawn sample cannot be renamed or withdrawn again.
- A withdrawal removes the sample from the corrected/visible longitudinal
  aggregation, while the original facts, the raw report decision and every
  historical knowledge version remain intact.
- In one package, candidate report facts are added first and corrections are
  then validated in array order and committed together, so a correction may
  target a report imported in the same manifest. Any failure rolls back the
  reports, source links, corrections and knowledge sequence as a unit.

## 4. Knowledge versions

Every successful transaction that introduces a new canonical fact set, a new
raw snapshot/source relationship, or a new correction receives the next
contiguous `knowledge_seq` in `knowledge_ledger`. A pure idempotent replay adds
no sequence. A transaction that only adds a source link is recorded as a
`source_only_transaction`; one that adds facts or corrections is a
`fact_transaction`.

All writes run in one SQLite `BEGIN IMMEDIATE` transaction, so controlled
concurrent imports serialize on the single-writer lock and never produce
duplicate sequences or partial commits. Schema creation on a missing database
is performed inside the same kind of immediate transaction. A pre-existing
database with an incompatible or unrelated schema is rejected; the file is
never silently dropped and rebuilt.

## 5. Report-only queries

`--report` opens the database read-only and never creates it. Options:

- `--knowledge-seq K`: rebuild the view as of sequence `K`. Omit it for the
  latest version. Non-positive or future sequences fail.
- `--batch B`: optional exact batch filter.
- `--output PATH`: write stable JSON after fully serializing it, then atomically
  replace via a same-directory temp file and `os.replace`. A failure never
  overwrites an existing output, and report-only failures do not touch the
  database.

The output contains the warehouse schema, the actual and latest knowledge
sequences, the import/report/correction sources used, an `original_view`
(samples, QC, QC scopes, summary, original reportable decisions and reasons),
a `corrected_view` (current name, withdrawn flag, immutable original identity,
the correction history with reasons, and the originating report), a
`longitudinal_summary` across unwithdrawn captured reports, and
`longitudinal_changes`.

The longitudinal change record compares only the **original** decisions of the
same immutable business key across adjacent canonical snapshots and reports
whether `mean`, `reportable`, `reasons` and `calibration_ids` changed. Legacy
and timed reports can sit side by side; missing legacy fields are represented
as `null`/empty collections rather than treated as a change to an empty value.
Renames and withdrawals never alter this original change chain.

Identical database content, sequence and filter produce byte-identical JSON:
no current time, absolute path or SQLite rowid is included. Output failure does
not roll back an already committed import; the operator can rerun report-only.

## 6. Self-containment and recovery

The database retains captured manifest bytes, canonical manifest text, raw
report bytes, canonical fact JSON, SHA256 digests, source labels and correction
reasons. After the manifest and report files are moved away, every fact and
provenance relationship is still queryable, and table facts are provably tied
to captured report bytes through the raw/canonical hashes.

All validation and writes complete inside one transaction; SQLite errors,
constraint failures or pre-commit exceptions roll the whole import back and
discard temporary outputs. A corrected manifest can be rerun with the same
command. Failure recovery never deletes and recreates an existing database.

## 7. Example workflow

The committed synthetic package under `examples/warehouse/` contains three
generated reports and four manifests. Using a scratch database (do not commit
database files):

```sh
DB=/tmp/assay-demo.sqlite
python -m assay_insights.warehouse --db "$DB" \
  --manifest examples/warehouse/IMP-001-legacy.json
python -m assay_insights.warehouse --db "$DB" \
  --manifest examples/warehouse/IMP-002-timed.json
python -m assay_insights.warehouse --db "$DB" \
  --manifest examples/warehouse/IMP-003-rename.json
python -m assay_insights.warehouse --db "$DB" \
  --manifest examples/warehouse/IMP-004-rerun.json

# Latest view, and the decision as of the first knowledge version.
python -m assay_insights.warehouse --db "$DB" --report --output /tmp/latest.json
python -m assay_insights.warehouse --db "$DB" --report \
  --knowledge-seq 1 --output /tmp/seq1.json
```

The first manifest imports the schema 1 legacy report; the second imports the
schema 2 timed report; the third renames an ordinary sample while keeping the
raw report byte-for-byte; the fourth imports a later timed rerun in which the
same original `B1/S1/nitrate` key keeps mean `4.600000` but becomes
unreportable (`replicate_rsd_exceeded`). The longitudinal change record shows
the reportable/reasons transition without treating the rename as a computed
change.

## 8. SQLite tables

| Table | Grain / purpose |
| --- | --- |
| `warehouse_meta` | Warehouse schema version marker. |
| `knowledge_ledger` | Contiguous `knowledge_seq` per committed import and its kind. |
| `imports` | Captured and canonical manifest bytes per `import_id`. |
| `canonical_fact_sets` | One normalized fact set per canonical report hash. |
| `report_snapshots` | One raw captured byte stream per report hash, linked to its canonical set. |
| `import_reports` | Many-to-many source links: import, report hash, label, path label, ordinal. |
| `fact_sample_groups` | Ordinary sample group statistics, reasons, reportable, calibration ids. |
| `fact_qc_groups` | QC (sub)groups, recovery, target and pass/fail outcome. |
| `fact_qc_scopes` | Schema 2 batch/analyte/calibration QC eligibility. |
| `fact_batches` | Schema 1 batch/analyte QC rollups. |
| `fact_calibrations` | Schema 2 calibration version catalog. |
| `fact_measurements` | Schema 2 per-measurement identity, time, version and concentration facts. |
| `sample_identities` | Immutable ordinary-sample business keys per raw report. |
| `corrections` | Ordered rename/withdraw events per identity and knowledge sequence. |
